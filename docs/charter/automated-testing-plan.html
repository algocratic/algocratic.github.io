GREEN · Charter packet · Proposed test architecture

Automated Testing Plan

A staged quality system for static portal pages: first make every revised artifact independently reviewable from disk, then earn confidence in structure, access, meaning, and presentation.

teacherbot@green · frozen iteration

Mandate and present boundary

This document proposes an automated testing stack; it does not install, configure, or run that stack. For this iteration, “the site works” means an external reviewer can open each revised page directly from the repository filesystem and inspect its content. A web server, build step, deployment, and working legacy portal navigation are not acceptance requirements.

In scope

Revised charter and portal pages, their relative local dependencies, document semantics, visible content, accessibility, design-system use, and representative rendering.

Explicitly deferred

Repair of unrelated portal routes, production deployment, application behavior, the agent kernel, and implementation of this testing proposal.

Review rule: portal pages may be reviewed during this pass. Incidental findings are recorded for later reading; they do not expand this iteration’s remediation scope.

Test principles

  • Local-first: all revised pages open via file://; internal page, stylesheet, image, and document references resolve without a server.
  • Layered evidence: fast deterministic checks run before browser checks, so failures identify the smallest useful cause.
  • Semantic color: PRISM colors are checked as capability, clearance, ownership, or audience-complexity signals—not decoration.
  • No invisible success: CI produces human-readable summaries and machine-readable artifacts even when a gate fails.
  • Progressive enforcement: the initial baseline records legacy defects; hard gates apply to revised files and regressions unless the contract later broadens scope.

Critical review journeys

  1. Open from disk. Load each revised HTML file directly, with no local server and network disabled. The page remains readable even if hosted webfonts are unavailable.
  2. Traverse the charter packet. Follow relative links from the charter index to the PRISM crosswalk, agent-kernel plan, plan ASSAY, automated-testing plan, and review findings; return without a broken target.
  3. Inspect sources and limits. A reviewer can identify provenance, timestamp, assumptions, known limits, status, and the teacherbot@green stamp on every charter artifact.
  4. Use without a pointer. Keyboard navigation exposes a visible focus indicator, logical focus order, and no keyboard trap.
  5. Read across viewports. At 360×800, 768×1024, and 1440×900, text remains legible, tables remain reachable, and the page does not create unintended horizontal document overflow.
  6. Review legacy pages without scope creep. Crawl agreed portal pages in report-only mode and write findings for later interpretation, without making their defects fail this iteration.

Acceptance gates

Gate 01 · Disk

Locally complete

Every revised page and required local asset exists; relative links and fragments resolve from disk. External sources are labeled and do not prevent core reading.

Gate 02 · Structure

Valid and identifiable

Revised HTML passes the validator and supplies language, unique title, viewport metadata, one clear page heading, ordered headings, and appropriate landmarks.

Gate 03 · Integrity

Contract fields present

Each charter page exposes its sources, timestamp, assumptions, known limits, deliverable state, and teacherbot@green stamp.

Gate 04 · Access

No severe automated barriers

No serious or critical axe violations; keyboard and 200% zoom smoke reviews pass. Automated checks never replace a recorded human review.

Gate 05 · System

Design language traceable

The canonical design-system stylesheet resolves; required document tokens and semantic PRISM treatments are detectable; unsupported decorative clearance color is absent.

Gate 06 · Render

Representative browsers stable

Critical journeys pass in current Playwright Chromium, Firefox, and WebKit projects at mobile, tablet, and desktop widths with no uncaught errors.

Gate 07 · Evidence

Failure is reviewable

CI reports the failing file, rule, severity, reproduction command, and relevant artifact. Screenshots, traces, and reports are retained for the agreed review window.

Gate 08 · Scope

Legacy breakage contained

Known surrounding portal failures and incidental review findings appear in a non-blocking report. New regressions in revised files remain blocking.

Design-system conformance model

Automated conformance is intentionally narrow. It can prove that pages load the canonical stylesheet, use approved custom properties, expose required typography and focus states, and reserve PRISM color for declared semantic elements. It cannot determine whether a metaphor is appropriate, a page is genuinely comprehensible to its intended audience, or a color choice communicates the correct organizational meaning.

Those questions require a human review using the PRISM/design-system crosswalk. The reviewer records the intended audience rung, the page’s cognitive and ownership demands, observed mismatches, and a disposition: accept, revise in a later iteration, or escalate for negotiation.

CI sequence and reporting

  1. Discover change scope. Compare revised paths to the base revision and combine them with the explicit charter manifest.
  2. Run deterministic checks. Validate markup, resolve local targets, and enforce content and design-system invariants.
  3. Run browser checks. Execute accessibility and journey tests across the browser matrix, then capture diagnostics on failure.
  4. Publish one receipt. Produce a Markdown job summary plus JUnit, axe JSON, link results, screenshots, and Playwright traces as artifacts.
  5. Separate signal. Mark revised-page gate failures as blocking; list legacy observations under “deferred portal findings” without changing the result.

Pull requests receive a concise gate table and links to artifacts. Main-branch runs retain a longitudinal baseline so newly introduced failures can be distinguished from recorded legacy conditions. Secrets, user data, and absolute developer paths must not appear in artifacts.

Required human review

The future implementation must use the INDIGO accessibility test framework for run manifests, evidence fields, manual review, and honest terminal status.

  • Read the page at its declared PRISM audience level and assess cognitive load, prerequisites, and organizational scope.
  • Confirm meaning is not communicated by color alone and that GREEN denotes independent delivery rather than decoration.
  • Inspect keyboard flow, 200% zoom, print behavior, and a screen-reader landmark/heading summary.
  • Confirm satirical voice does not obscure operational instructions, status, provenance, or known limits.
  • File portal observations for a later pass; do not remediate incidental legacy findings during this iteration.

Implementation sequence

  1. Baseline: define the page manifest, validate revised files, crawl agreed legacy pages in report-only mode, and approve initial screenshots.
  2. Gate: add link, content-integrity, axe, keyboard, and browser journey checks; make revised-page regressions blocking.
  3. Conform: encode stable design-system invariants and add the human PRISM review form; keep subjective judgments outside automated pass/fail logic.
  4. Operate: schedule dependency updates, baseline review, flaky-test quarantine with expiry, artifact retention review, and periodic assistive-technology checks.
