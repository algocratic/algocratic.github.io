Agent-Organization Kernel Implementation Plan

A bounded plan for implementing the smallest deterministic coordination kernel that can drive a finite workflow to completion, detected deadlock, bounded failure, or a justified and recorded refusal.

01 · Objective and claim boundary

Implementable objective

Completion or an explicit terminal account

Build a deterministic, simulator-first kernel for one to nine agents operating on finite directed workflow graphs. Every admitted run must finish as COMPLETED, REFUSED, DEADLOCKED, FAILED, or BOUND_EXCEEDED.

Exclusions

No unrestricted organization hiding inside

The kernel does not add open-ended planning, natural-language negotiation, mutable graphs, global knowledge by default, distributed consensus, or guarantees during an unbounded network partition. Ten or more agents are outside this iteration.

This document is a plan. It describes the proposed kernel and its verification obligations; it does not implement the kernel or claim that any test currently passes.

02 · Deterministic kernel model

The protocol separates message syntax, transition logic, task contracts, transport, and evidence. One accepted token in one state may select at most one guarded transition. Ambiguous transition tables fail validation before a run begins.

STATES: IDLE, OFFERED, COMMITTED, RUNNING,
        DONE, REFUSED, FAILED, RECOVERING

TOKENS: OFFER, ACCEPT, REJECT, START, RESULT, FAIL,
        ACK, TIMEOUT, RECOVER, AMEND, CANCEL

IF valid(token, state, contract, sender, receiver)
THEN apply_transition_and_emit
ELSE refuse_and_record
Transition definition

Every row declares current state, accepted token, guard, action, next state, emitted token, precondition, postcondition, refusal reason, and record event.

Local view

An agent reads its state, contract, owned tasks, direct neighbors, addressed messages, relevant record entries, and configured bounds. Full-graph access requires an explicit role grant.

03 · Workflow, ownership, amendment, and failure model

Admitted workflow class

Finite directed graphs

  • One start node, one or more terminal nodes, finite task nodes, explicit edges.
  • Immutable graph during execution, explicit contracts and one active owner per task.
  • Acyclic graphs first; bounded cycles only after every acyclic obligation passes.
  • Readiness requires all required predecessors to complete.
Asynchronous communication

Adversity, but bounded

  • Delay, reorder, duplicate, and drop messages within configured limits.
  • Crash-stop an agent; optionally restart it when recovery is enabled.
  • Configure maximum failed agents, dropped messages, delay, retries, and recovery transitions.
  • Exceeding any bound ends in a recorded BOUND_EXCEEDED outcome.

Ownership and amendment discipline

Ownership transfers require both OWNER_RELEASED and OWNER_ACCEPTED events; concurrent active ownership is refused. Amendments require an authorized AMEND token before affected work starts and record the old and new contract hashes, authority, clauses changed, reason code, and sequence. Completed tasks and unrecorded amendments are immutable.

Recovery and deadlock

Message identifiers make handling idempotent. Duplicates are recorded and ignored after their first effect. Recovery replays the authoritative record to restore agent state and may cover one dropped message, duplicated message, reordered pair, crash, restart, and ownership transfer within configured bounds.

Deadlock exists only when unfinished work remains, no valid transition is enabled, no permitted message is in transit, and no remaining timeout or recovery action can make progress. The detector waits for configured delay bounds, then records blocked tasks and failed guards before returning DEADLOCKED.

06 · Test strategy

Unit

Exercise every valid and invalid state-token pair, guard, refusal code, schema validator, hash link, timeout, retry, ownership transfer, duplicate, and amendment authorization.

Property

Prove one active owner, guarded transitions only, postconditions before completion, visible amendments/refusals, terminal status for every run, stable replay, and idempotent duplicates.

Model-based

Generate small graphs for one to nine agents, explore all enabled transitions within bounds, compare traces to the formal model, and report unreachable or exitless states and unused tokens.

Integration and replay

Cover linear, fork, join, parallel, transfer, retry, bounded cycle, deadlock, refusal, amendment, crash/restart, and delivery faults; rebuild deleted runtime state from each saved log.

Required agent-count matrix

AgentsRequired graph forms and stressors
1Three-task linear completion, invalid-token refusal, bounded retry.
2Handoff, dual-event ownership transfer, dropped acceptance.
3Fork, join, one failed agent, unauthorized amendment.
5Parallel branches, delayed and duplicated messages.
7Mixed ownership, bounded recovery, reordered messages.
9Fork, join, transfer, delay, one crash; largest initial stress graph.

Every scenario uses a deterministic seed. Failures preserve the seed and complete event record. The baseline also includes a circular-dependency deadlock and a duplicate RESULT that completes exactly once.

Minimality experiments

After the baseline passes, remove one state, token, contract clause, graph primitive, or refusal code at a time; run the full suite; record the first property lost; then restore it. Classify each element as REQUIRED, DERIVABLE, REDUNDANT, or UNDECIDED. “Minimal” is permitted only when every retained element is required or formally derived—not merely because the source is short.

07 · Implementation sequence and deliverables

  1. Write formal state, token, task-contract, event, and refusal definitions.
  2. Define and mechanically validate the deterministic transition table.
  3. Implement contract and graph validation, then the append-only record.
  4. Implement the single-agent simulator and pass all one-agent tests.
  5. Add seeded asynchronous messaging and two-agent ownership transfer.
  6. Add three-agent fork/join, then bounded delivery and crash fault injection.
  7. Add recovery, deadlock detection, and replay from an empty runtime.
  8. Extend scenarios to five, seven, and nine agents.
  9. Run destructive minimality experiments and document every lost property.
  10. Publish specifications, evidence, assumptions, failures, and unresolved claims; ASSAY and SHIP occur in later authorized operations.

Planned implementation artifacts are docs/kernel-spec.md, docs/failure-model.md, docs/test-plan.md, docs/minimality-results.md, src/, tests/, examples/, artifacts/test-records/, and a kernel README.md. Their repository location and language remain open decisions.

08 · Acceptance gate

  • Supported workflows execute with one to nine agents and every run records exactly one terminal status.
  • Every refusal uses a valid bounded reason code; every amendment is authorized and recorded.
  • Every task has at most one active owner and every completed task passes its postconditions.
  • Bounded failures recover or produce an explicit terminal account; deadlock is absent or detected.
  • Replay reproduces final state, and equal inputs plus seeds produce equal transition traces.
  • The full suite identifies the property lost after each destructive reduction.
  • Documentation states environmental assumptions and makes no guarantee outside the configured model.
Assumptions
  • Use a deterministic simulator before threads or processes.
  • Use one authoritative append-only record initially.
  • Crash-stop is the first agent-failure model.
  • Time is represented by deterministic logical ticks or event sequence.
Known limits and open decisions
  • Programming language, test framework, and implementation repository path are not selected.
  • The first pass does not use real concurrent processes or claim distributed consensus.
  • Bounded cycles wait until all acyclic tests pass.
  • Formal support for minimality and the joint research foundations require later ASSAY.
